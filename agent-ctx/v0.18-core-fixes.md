# Task v0.18-core-fixes — Resumen del subagente

## Tarea
Implementar 5 correcciones críticas:
1. Motor de estados centralizado para Order y OrderItem
2. Pizzería/cocina por `targetAreaId` (no por `order.area.code`)
3. Consumo de recetas automático al marcar item como LISTO
4. Stock insuficiente configurable (`blockNegativeStock` en RestaurantConfig)
5. Generación segura de números de pedido (transacción atómica con `OrderSequence`)

## Archivos creados

### 1. `src/lib/order-state-machine.ts`
Centraliza todas las transiciones válidas de estados.

- `ORDER_TRANSITIONS: Record<OrderStatus, OrderStatus[]>` — Mapa estricto tipado con todas las transiciones válidas para Order:
  - CREADO → [ENVIADO, CANCELADO]
  - ENVIADO → [EN_PREPARACION, CANCELADO]
  - EN_PREPARACION → [LISTO]
  - LISTO → [SERVIDO, EN_PREPARACION]
  - SERVIDO → [COBRADO]
  - COBRADO → [ARCHIVADO]
  - ARCHIVADO → []
  - CANCELADO → []
- `ITEM_TRANSITIONS: Record<OrderItemStatus, OrderItemStatus[]>` — Transiciones válidas para OrderItem:
  - PENDIENTE → [EN_PREPARACION, CANCELADO]
  - EN_PREPARACION → [LISTO, CANCELADO]
  - LISTO → [SERVIDO]
  - SERVIDO → []
  - CANCELADO → []
- Funciones exportadas:
  - `canTransitionOrder(from, to): boolean`
  - `canTransitionItem(from, to): boolean`
  - `getValidOrderTransitions(status): string[]`
  - `getValidItemTransitions(status): string[]`

### 2. `src/lib/recipe-consumer.ts`
Función `consumeRecipe(productId, quantity, areaId, orderId, orderItemId, userId): Promise<ConsumeRecipeResult>` que descuenta los ingredientes de la receta del inventario.

- **Idempotencia**: usa `reference = recipe-sync:${orderItemId}` en StockMovement. Verifica AMBOS formatos:
  - Nuevo: `recipe-sync:${orderItemId}` (especificado en FIX 3)
  - Legacy: `recipe-sync:${orderId}:${orderItemId}` (compatibilidad con sync-recipe endpoint existente)
  - Si ya existe StockMovement con cualquiera de las dos referencias, retorna `{ ok: true, alreadySynced: true }` sin descuentar.
- **Sin receta**: crea StockMovement "marcador" con `quantity=0` para garantizar idempotencia futura, retorna `{ ok: true, noRecipe: true }`.
- **Cálculo de escala**: `scale = quantity / recipe.yield`. Cada ingrediente se descuenta `ingredient.quantity * scale` (redondeado a 4 decimales).
- **Por cada ingrediente** (en transacción Prisma):
  1. Determina área: `ingredient.product.areaId || areaId` (targetAreaId del item)
  2. Busca `AreaInventory` para (área, ingredient.productId).
  3. Si existe: `decrement` (puede quedar negativo). Si `stockBefore < quantityNeeded` → alerta.
  4. Si no existe: fallback a `InventoryItem` general (con alerta).
  5. Si tampoco existe: alerta "no tiene inventario registrado".
  6. Crea `StockMovement` con `type=SALIDA`, `reference=recipe-sync:${orderItemId}`.
- Retorna `{ ok, deductionsCount, alertsCount, alerts, deductions }`.

## Decisiones técnicas

1. **State machine tipado estricto**: Usé `Record<OrderStatus, OrderStatus[]>` en lugar de `Record<string, string[]>` para que TypeScript detecte en compilación si una transición inválida se añade por error.

2. **Idempotencia cross-endpoint**: consumeRecipe y sync-recipe usan AMBOS formatos de `reference` (nuevo `recipe-sync:${orderItemId}` y legacy `recipe-sync:${orderId}:${orderItemId}`) para que:
   - Items ya sincronizados por versiones anteriores no sean re-procesados.
   - Items auto-consumidos por consumeRecipe no sean doble-descontados por sync-recipe manual.
   - Items sincronizados manualmente por sync-recipe no sean re-procesados por consumeRecipe en reintentos.

3. **consumeRecipe fuera de la transacción principal**: la transacción de cambio de estado del item no incluye el descuento de receta. Esto evita que un fallo de inventario bloquee el flujo de cocina (que es prioritario). Si consumeRecipe falla, se loguea pero el item queda en LISTO.

4. **blockNegativeStock solo para DIRECTO**: los productos FINALES descuentan al prepararse (vía receta en cocina), no al venderse. Validar stock en venta de FINAL sería incorrecto porque la receta define qué ingredientes se descuentan.

5. **OrderSequence con fallback**: aunque el upsert atómico garantiza números únicos en condiciones normales, añadí un fallback `if (exists) { lastOrder.number + 1 }` para bases migradas desde versiones anteriores donde ya existían pedidos sin la secuencia inicializada.

## Para subagentes posteriores

- `src/lib/order-state-machine.ts` puede usarse en cualquier endpoint que necesite validar transiciones de estado. Importar: `import { canTransitionOrder, canTransitionItem, getValidOrderTransitions, getValidItemTransitions } from '@/lib/order-state-machine'`.
- `src/lib/recipe-consumer.ts` puede usarse desde cualquier endpoint que necesite descontar receta. La función es idempotente.
- `RestaurantConfig.blockNegativeStock` puede togglearse desde el panel admin de configuración (PATCH /api/admin/config con `{ blockNegativeStock: true }`).
- `OrderSequence` se inicializa automáticamente en el primer POST /api/mesero/orders (upsert create con nextNumber=1001).
- Para ver los movimientos generados por consumeRecipe: `db.stockMovement.findMany({ where: { reference: { startsWith: 'recipe-sync:' } } })`.
